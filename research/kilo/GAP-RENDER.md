# Пробел между «правило как запись» и «файл, который читает Kilo»

> **Исторический анализ:** актуальные цели и приоритет решений владельца — [ROADMAP.md](ROADMAP.md) v4.0.0; прежние оценки не являются текущим вердиктом.

**Дата:** 2026-11-24 · **Основание:** остановка владельца на `INSTALL-KILO.md` шаг 2–3
**Суть:** у Kit есть модель правила и нет **внедрения** правила в среду.

## 1. Что уже существует (проверено по репозиторию, не по памяти)

| Слой | Где | Что даёт | Единица |
|---|---|---|---|
| Формат записи | `kit/base/SCHEMA-V2.md`, `schema_v2.py` | `id`, `kind`, `state`, `parent`, `scope`, `title`, `text`, `basis`, `criterion`, `key`/`value`; области L0/L1/L2 | **запись** |
| Карточка операции из фразы | `OPERATION-CARD.md`, `operation_card.py` | разбор обычной фразы, `missing[]`, вопросы | карточка |
| План и дифф | `OPERATION-PLAN.md`, `operation_plan.py` | точный дифф, билет, запись по согласию | план |
| Перенос L2→L1 | `PROMOTION.md`, `promotion.py` | кандидат-черновик переносимой редакции | **редакция** |
| Имитация внедрения | `SIMULATION.md`, `simulation.py` | две синтетические фикстуры (`cli`, `docs`), проверка, что правило доходит до двух сред | фикстура |
| Конфликты | `CONFLICT-REVIEW.md`, `conflict_review.py` | показывает конфликт, **не выбирает победителя** | отчёт |
| Пакет/целостность/откат | `BUNDLE*.md`, `bundle*.py` | срез, сверка, доверие, откат N−1 | пакет |

## 2. Чего НЕТ

**Ни один модуль не превращает запись Kit в файл, который читает Kilo.**

Проверка: `simulation.py` работает с байтами и фикстурами внутри стенда и **явно** не пишет в проекты.
`promotion.py` готовит черновик и не выдаёт путь для записи. Установка в реальный проект отсутствует
как функция.

Отсюда и остановка: `INSTALL-KILO.md` шаг 3 говорит «положите правило в `.kilo/rules/`», но:
- какая **единица** туда кладётся — одна запись? набор записей одной области? производный файл?
- в каком **формате** — Markdown с заголовком из `title` и телом из `text`? JSON? несколько правил в файле?
- что происходит с `scope` — он превращается в путь или остаётся полем?
- что делать с `parent` и `id` — они вообще нужны среде, которая читает только текст?
- как **проверить**, что внедрено именно это правило, а не «текст похож»?

## 3. Вывод, который из этого следует

`INSTALL-KILO.md` — это **рецепт доставки**, а не установки. Он верен в части механизма Kilo
(`kilo.jsonc` + `.kilo/rules/` + проверка цитатой) и пуст в части предмета доставки.

Поэтому правильный порядок:

1. **сначала** определить единицу и формат внедрения (рендер записи → файл среды);
2. **потом** пройти имитацию (`SIMULATION.md`) с **реальным** рендером, а не синтетической фикстурой;
3. **только затем** возвращаться к `INSTALL-KILO.md` и проходить его целиком.

## 4. Что нужно решить владельцу (это решение, не находка)

| Вопрос | Варианты | Цена каждого |
|---|---|---|
| **Единица внедрения** | (а) одна запись = один файл; (б) одна область (L2 проекта) = один файл со всеми записями; (в) контракт = файл, дочерние записи внутри | (а) много файлов, точный `scope`; (б) меньше файлов, но смена одного правила переписывает весь файл; (в) соответствует `parent`, но теряется плоский поиск |
| **Формат файла** | (а) Markdown: `# title`, тело `text`, служебные поля в комментарии; (б) Markdown без служебных полей; (в) JSON + отдельный рендер в Markdown | (а) трассируемость к `id`, но среда видит «мусорные» строки; (б) чисто для среды, но связь с реестром теряется; (в) два артефакта вместо одного |
| **Что делает `scope`** | (а) префикс пути файла; (б) строка внутри файла; (в) не переносится (среда не умеет) | (а) работает вложенность; (б) среда не понимает; (в) правило применяется шире, чем задумано |
| **Проверка внедрения** | (а) цитата в чате (как в шагах 5); (б) сверка хеша файла с ожидаемым; (в) и то и другое | (а) доказывает загрузку, не совпадение; (б) доказывает файл, не загрузку; (в) дороже, но полнее |
