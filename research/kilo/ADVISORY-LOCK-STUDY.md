# Исследование advisory-блокировки между процессами

**Не исправление `.27`, не код записи Kit и не доказательство безопасности.**
`research/audit/test_advisory_lock_study.py` запускает отдельные процессы Python с ограниченным
временем ожидания и синхронизацией, используя только новые файлы в одном временном каталоге.
В процессе-владельце и дочернем процессе применён POSIX `flock(LOCK_EX | LOCK_NB)`; полученные
результаты относятся к конкретному эксперименту, а не к любой разновидности блокировки.
Кандидат, PlanSession, входные реестры, билет и реальная конкурентная нагрузка не выполняются.

## Наблюдения

Linux 6.1.158+ x86_64, Python 3.11.2, `/tmp` ext4: семь адресных тестов, без пропусков.
Отсутствие POSIX API или ошибки неподдерживаемой операции в предварительной пробе `flock`
отмечаются `not_run`; неожиданные ошибки, таймауты или отказы самих сценариев — ошибки.

| Проба | Результат |
|---|---|
| Два кооперативных процесса открывают один существующий lock-файл | Пока первый удерживает эксклюзивный `flock`, второй получает `busy`; после явного снятия второй получает блокировку. |
| Второй процесс без запроса блокировки пишет в сам заблокированный синтетический файл | Запись проходит, байты меняются, попытка второго процесса получить блокировку прежнего объекта по-прежнему `busy`. |
| Второй процесс без блокировки заменяет заблокированный файл через `os.replace` | Новые байты видны по имени, старый открытый объект остаётся заблокированным; процесс, открывший новое имя, получает отдельную блокировку. |
| Отдельный lock-файл удерживается, второй процесс игнорирует его | Второй процесс заменяет синтетический реестр или изменяет синтетический подготовленный файл; исходный lock всё ещё `busy`. |
| Lock-файл перемещён, на его старом имени создан новый | Попытка блокировки старого объекта `busy`, нового — успешна одновременно. Это разные объекты, хотя участники могут считать, что используют одно имя. |
| Процесс-владелец блокировки принудительно завершён | На данном стенде другой процесс после завершения смог получить блокировку. Состояние реестра/восстановление прерванной записи в этой пробе не проверяется. |

Проба показывает координацию при конкретной общей дисциплине, но не принудительное исключение
посторонних записей. Блокировка самого реестра не автоматически переносится на новый объект,
созданный заменой; отдельный lock-файл требует в том числе стабильной привязки и прав на
каталог и сотрудничества всех писателей. Это не предложение просто добавить `flock` в `.27`.

## Границы и дальнейшая работа

Отдельно определить модель доверия, полномочия и жизненный цикл блокировки, защиту и привязку
объекта блокировки, все точки чтения/проверки/записи, поведение при ошибке и восстановление.
Эти вопросы не решаются демонстрацией `busy`. Сети, другие ФС/ОС, другие пользователи,
права/ACL, дедлоки, наследование дескрипторов, power failure, доказательство сохранности
данных и опасное вмешательство в реальные профили — `not_run`. Даже корректная кооперация
не препятствует участнику, который имеет права записи и игнорирует договорённость. Системные
детали и возможные аналоги на иных платформах требуют отдельных исследований.

D02/D03, политика метаданных, доверенная доставка и G1–G6 остаются открыты; локальный pin
не удостоверяет происхождение. Предыдущее [исследование dir_fd](DIRFD-RACE-STUDY.md) не
является реализацией блокировки или доказательством отсутствия гонок.
