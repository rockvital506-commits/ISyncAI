# Стратегия хранения и навигации: архитектура досье Kilo

**Дата:** 2026-11-22 · **Область:** `research/kilo/` · **Не итерация**

## 1. Задача, которую решает эта архитектура

Досье должно отвечать на три вопроса быстро и дёшево:

1. **Что это?** — сущность Kilo и допустимые значения.
2. **Какое состояние нужно?** — сущность **с конфигом**, пригодная для сценария.
3. **Что делать при ветвлении?** — если версия/источник/права другие, какой сценарий выбрать.

Ограничение по P8: каталог всегда читается, тела — по требованию. Поэтому слои разделены по
**стоимости чтения**, а не по теме.

## 2. Пять слоёв (снизу вверх по стоимости)

| Слой | Файл | Размер | Когда читается | Что даёт |
|---|---|---|---|---|
| **0 · Каталог** | `CATALOG.json` | малый | всегда | по одной строке на сущность/состояние/сценарий |
| **1 · Спецификация** | `KILO-SPEC.json` | средний | при сборке конфига | значения, границы, инварианты, машинно проверяемо |
| **2 · Сущности** | `ENTITIES.json`, `ENTITIES-2.json`, `ENTITIES-3.json` | крупный | по требованию | определения, связи, влияние на поведение |
| **3 · Состояния** | `STATES.json` | средний | при выборе сценария | отпечаток конфига, ожидаемое/неожидаемое |
| **4 · Сценарии** | `SCENARIOS.json` | средний | при эксплуатации | цель, действие, наблюдение, ветки |
| **5 · Решения** | `DECISIONS.json` | малый | при быстрой справке | «задача → состояние → ключи → проверка» |

Свидетельства лежат отдельно и **не смешиваются** с данными: `SOURCES.json` (откуда),
`GAPS.md` (что противоречит), `SCREENS-*.md` (что видно).

## 3. Три индекса навигации

Индексы — это не копии, а ссылки. Каждый ответ содержит `id`, по которому открывается тело.

- **По сущности** — «где настраивается X»: `CATALOG.entities[id].file`
- **По состоянию** — «какой конфиг даёт состояние X»: `CATALOG.states[id].scenarios`
- **По пробелу** — «что мешает сценарию X»: `CATALOG.scenarios[id].blocked_by` → `GAPS.md#C*`

Обратный ход (диагностика): `spec_check.py --state` говорит, какое правило спецификации нарушено,
и выдаёт `id` сущности, где лежит объяснение.

## 4. Четыре фильтра ветвления

Применяются строго по порядку; неопределённый фильтр останавливает выбор.

| # | Фильтр | Значения | Источник |
|---|---|---|---|
| Ф1 | Поверхность и эра | VS Code 7.x (на CLI) / прежняя 4–6.x / CLI / JetBrains / web | `ENT-ENV.architecture_era` |
| Ф2 | Источник входа | `agent.prompt` → `instructions` проекта → `AGENTS.md` → `instructions` глобально → skills | `ENT-RULES.priority` |
| Ф3 | Права | пресет (`Review first` / `High autonomy`) + правила по инструментам | `ENT-WORKSTYLE`, `ENT-PERM` |
| Ф4 | Модель и лимит | `limit.context`, `limit.output`, порог сжатия | `ENT-MODELS`, `ENT-COMPACTION` |

Ф4 добавлен по наблюдению: без объявленного `limit.context` автосжатие **не работает**, и сценарий
«длинная задача» ведёт себя иначе. Раньше этого измерения в досье не было.

## 5. Алгоритм формирования состояния (главное)

Состояние = сущность с конфигом. Семь шагов, каждый проверяем:

1. **Задача** → выбрать сценарий `SC-*` из `DECISIONS.json`.
2. **Среда** → Ф1: зафиксировать версию и поверхность. Нет версии → стоп `not run`.
3. **База** → взять ближайшее состояние `ST-*` как отправную точку.
4. **Сборка** → наложить ключи из карточки решения, соблюдая `KILO-SPEC` (только известные ключи).
5. **Проверка** → `python3 -B spec_check.py --state state.json`: ноль ошибок, пробелы перечислены.
6. **Отпечаток** → записать минимальный набор полей в `STATES.json` как новое состояние.
7. **Наблюдение** → выполнить действие и записать **что видно**, а не что ожидалось.

Правило шага 5: **неизвестный ключ — ошибка, а не «наверное, подойдёт»**. Это защита от выдумки,
симметричная P13 (поверхность по реестру, не по совпадению слов).

## 6. Разделение с Kit

| Что | Где | Почему |
|---|---|---|
| Правила, операции, инварианты Kit | `kit/`, `research/STRATEGY.md` | ориентир остаётся единственным планом |
| Факты о среде Kilo | `research/kilo/` | это данные, не обязательства |
| Точки входа Kit в среду | ссылка на `kit/base/entry.txt` из досье | не копируем текст, не создаём второй реестр |

Досье **не содержит** правил Kit, их копий и альтернативных профилей. Оно ссылается по пути.

## 7. Правила пополнения (без них архитектура деградирует)

1. Одна запись = один `id` + `checked` + `level`. Без даты не добавляется.
2. `vendor` и `observed_ui` не смешиваются в одном поле; противоречие → `GAPS.md`, обе стороны.
3. Число из документации не становится числом проекта: в `KILO-SPEC` только то, что объявлено
   поставщиком с явной пометкой `source: vendor-doc`.
4. Новое наблюдение не переписывает старое: добавляется `observed_ui`-блок с датой.
5. Если слой 0 (каталог) расходится с телом — прав каталог, тело перечитывается.
6. Скриншот даёт только видимое: настройки, версии, подписи. Никаких «агент прочитал».

## 8. Что эта архитектура сознательно не делает

- Не хранит полные тексты документации (только утверждение + ссылка + дата).
- Не считает досье за прогон: `observed_ui` ≠ `observed`.
- Не меняет план: см. `REVISION-2026-11-22.md`.
- Не автоматизирует установку, запуск клиента или правку настроек.
- Не превращается в «второй реестр»: все ссылки наружу, вся правда о Kit — в `kit/`.
