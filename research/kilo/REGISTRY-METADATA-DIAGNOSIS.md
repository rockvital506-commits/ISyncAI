# Диагностика метаданных при записи L1/L2

**Наблюдение на синтетическом POSIX-стенде, не исправление и не проверка прав доступа.**
Для работы с реальными профилями нужно отдельно определить политику прав и метаданных,
согласие, ограничения среды и восстановление. Нынешнее [описание хранилища](../../kit/base/STORAGE-V2.md)
уже не обещает сохранение прав ОС и ACL. Здесь выявляется конкретное следствие, которое нельзя
сводить к сохранению байтов реестров и истории.

## Изменение после диагностики

Наблюдения ниже выполнены на кандидате `.24`. В `.25` планируемые мутации `PlanSession`
получили `replacement_notice` в полном плане формата 2; уведомление не предсказывало и не
сохраняло метаданные. В `.26` план формата 3 также показывает на POSIX биты mode трёх
реестров и сравнивает их перед применением; при дрейфе — `stale_metadata` без записи. На
других ОС mode явно `not_checked`. Само сохранение mode при замене, ACL, владелец, группы,
xattr, права на каталоги и гонки не проверены. Прочие входы, в том числе нативный
`plan_create/apply_create`, не получают эти проверки от `PlanSession`. Вызывающий код должен
показать полный план, чего билет не доказывает.

## Почему исследовано

В `registry_store._replace` новый файл создаётся через `tempfile.NamedTemporaryFile` в каталоге
реестра; затем `os.replace` заменяет прежний файл. `PlanSession` показывает diff байтов,
ревизии и SHA-256 трёх реестров, проверяет повторно их байты и будущий diff. Режим доступа,
ACL, владелец и другие метаданные не включены в показанный diff или эти входные хеши. Хеш
байтов не меняется при `chmod`; согласие на показанный текстовый diff само по себе не говорит,
что человек увидел или одобрил изменение прав.

## Синтетические наблюдения

Сначала на `.24` проверено новое временное дерево с тремя фикстурными реестрами и POSIX
`umask 022`; прежний umask возвращался после каждой пробы. Таблица фиксирует именно
**исторические наблюдения `.24`**, а не требование сохранить поведение. На проверенной локальной ФС:

| Проба | Наблюдение |
|---|---|
| L1, mode `0640`, план и неподтверждённый apply | Без изменений в байтах и проверенных mode трёх реестров |
| Затем подтверждённая мутация L1 | Только байты L1 изменились, его mode стал `0600`; измеренный inode сменился. L0 и L2 сохранили байты и проверенные mode |
| Подтверждённая мутация L2 с mode `0644` | Только байты L2 изменились; его mode стал `0600`. L0 и L1 сохранили байты и проверенные mode |
| Цель L1 до операции уже `0600` | После подтверждённой мутации её mode остался `0600` |
| L1 после планирования изменён `chmod 0600 → 0640`, байты неизменны | План не отклонён как устаревший, подтверждённая замена снова дала `0600` |
| L2 после планирования изменён `chmod 0600 → 0640`, байты неизменны; цель L1 | Мутация L1 прошла; изменение mode L2 не включено во входные хеши и осталось неизменным |
| Искусственный отказ `os.replace` | Наблюдаемые байты и mode реестров сохранены, временный файл удалён, билет израсходован |

В `.24`/`.25` аналогичная проба изолированной сессии после смены mode допускала запись.
В `.26` обновлённый `test_registry_metadata_diagnosis.py` и новый `test_plan_mode_freshness.py`
отказывают при наблюдаемом дрейфе перед apply, включая сессию с отдельно скопированной парой;
также сохраняют пробы изменения mode после успешной замены. Они демонстрируют, что возврат
старого mode до проверки или изменение после проверки может пройти. Пара и хеши теста не
являются независимым доверием; пробы не гарантируют поведение других платформ и ФС.

Потенциальное последствие: в среде, где чтение через группу или другие mode-биты необходимо,
изменение может лишить другие процессы доступа; проверка самих прав этих процессов здесь не
проводилась. Уменьшение mode не доказывает конфиденциальность или сохранность других метаданных.
Меняются ли UID/GID, ACL, расширенные атрибуты, метки безопасности, ссылки, время и другие
свойства на конкретных ОС/ФС здесь не исследовано. Успех или отказ по одним mode-битам не
означает полной проверки разрешений. Условия других umask, Windows/NTFS, сетевых ФС, нескольких
пользователей, параллельных писателей и аварий питания — `not_run`.

## Требования к будущему решению, не выбранная политика

- Явно решить, какие назначения владения, mode и ACL допустимы, а какие должны вызывать отказ;
  нельзя безусловно расширять права нового файла или воспроизводить недоверенные ACL.
- Если метаданные входят в обязательства плана, определить представление пользователю,
  момент проверки и повторную проверку до записи, включая изменение цели и родителей. Это
  само по себе не закрывает гонку до замены; нужны отдельно выбранные пределы среды.
- Если режим только частного владельца является требованием продукта, его следует явно
  объявить и получить согласие **до** создания диффа/применения; изменение прав не должно
  происходить скрытно. Подходящий вариант для общего доступа требует отдельной политики.
- Рассмотреть состояние после отказа, повтор, совместимость с уже существующими данными,
  восстановление байтов **и** необходимых метаданных, поведение ACL, Windows и конкуренции.
  Нельзя считать один вызов `chmod` или успешный `os.replace` доказательством этого.

Политика сохранения или изменения прав и восстановление здесь не реализованы; сравнение mode
при планировании и применении не заменяет их. Нельзя автоматически исправлять реальные файлы
или расширять их права на основе этой пробы. D02–D06, D12, G1–G6 и живые среды остаются
открыты; реальные пользовательские деревья и исторические печати не изменяются.
