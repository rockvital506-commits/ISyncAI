# И‑103 — замысел и испытания (П0–П2)

**Сверка до работы (П0).** Ф0, §2, §3.2, §4 и §5 стратегии. У закреплённого выпуска 0.1.36 нет ни `profiles/` в дереве поставки, ни операций L1 в реестре CLI (ZIP выпуска и `research/strategy/BASELINE.json`). Формулировка И‑103 уточнена до реализации: десять мутаций выполняются на *стенде L1* рядом с установленным настоящим L0. Функциональная проверка L1 остаётся за И‑105/И‑106, миграция в 0.2.0 — за И‑131. A1–A4, состав P0 и порядок фаз не меняем.

**Замысел (П1).** Отделить три шкалы: SemVer выпуска, ревизию профиля и счётчик реального проекта. Закрепить матрицу совместимости и правила Git для локальной копии и Arena. Гипотеза: десять подтверждённых записей увеличат только `revision` стенда, а настоящие CLI 0.1.36 и байты источника/установленного L0 и L2 это не изменит. Политика не проводит миграцию и ничего не пишет в проект владельца. Изменения — только под `research/`. `.isai/`, исторические итерации и архив выпуска не меняются. Откат: отменить коммит этой итерации, не трогая пользовательские данные.

## П2. Сценарии и критерии

| ID | Сценарий | Критерий / ожидаемый отказ |
|---|---|---|
| T1 | Десять добавлений в отдельный стенд L1 (родительский контракт + новые правила) | Сохранённая ревизия 0 → 1 … → 10; при каждом шаге новый ID и новый digest правил; в двух файлах L1 нет SemVer |
| T2 | Проверка границ с реальным Kit 0.1.36 | Чистое `install → connect → create` без калибровки. Реальный `project_revision` повышается при `create`. `status.base.version`, pin, SHA дерева установленного L0 и L0 источника постоянны; весь проект побайтно неизменен при мутациях L1 |
| T3 | Повтор той же записи и запись по старой ревизии | Идемпотентный повтор с актуальной ревизией → `no_change`; устаревшее ожидание → стендовый `stale_revision`; никаких новых байтов, `revision` остаётся 10 |
| T4 | Матрица и пограничные значения | `0.1.36/schema 1` — единственный прямой кандидат на 0.2.0, но сама миграция `not run`; поставленные старые версии требуют отдельного подтверждения цепочки; неизвестная версия/схема → отказ без записи; обратный переход — только восстановление снимка, не downgrade |
| T5 | Настоящий 0.1.36 читает неподдерживаемую схему | В отдельном синтетическом проекте `status` может диагностировать состояние, но `plan` мутации обязан отказать, не меняя нанесённые тестовые байты; точный код сравнить с фактом CLI |
| T6 | Воспроизводимость и продолжение харнесса | Одинаковые результаты П3–П8 в checkout и в чистом снимке исходных файлов; сверка ZIP из конечного отчёта без перезаписи; И‑102 с её снимком по-прежнему воспроизводима |

Ожидания фиксируются в `test_versioning.py` и `ITERATION.json` до реализации пробы. Приёмка проваливается при любом дрейфе L0, молчаливой записи, ложной поддержке версии или расхождении с якорем. Живые среды, схема и CLI L1, настоящий переход/откат 0.2.0 — не предмет этой итерации.

Результат политики: [версии и совместимость](../strategy/VERSIONING.md), [машинная матрица](../strategy/COMPATIBILITY.json), [политика Git](../strategy/GIT-POLICY.md). Запуск: `python3 -B research/103/run.py`; повтор печати в том же снимке: та же команда с `--verify-seal`.
