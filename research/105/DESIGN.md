# И‑105 · Ф1 · P0 — физическая раскладка и одна запись L1

**П0. Сверка до работы.** База `71f5b10`, [стратегия v1.6](../STRATEGY.md), §1.5, §3.1–3.3, Ф1, §5. [И‑104](../104/ACCEPTANCE.json) приняла v2 как контракт данных; она не писала реестры и не проверяла реальные пути. [Стенд И‑103](../103/VERSION-EVIDENCE.json) измерял стендовые изменения двух файлов L1, а не путь записи целевого Kit. В И‑105 зависимости выполнены, расхождения с планом до работы нет.

**П1. Гипотеза.** При явно выбранном профиле и существующих трёх корнях целевой Kit сможет прочитать оба счётчика и провести одну согласованную запись в L1: `profile_revision: 0 → 1`, `project_revision: 7 → 7`, SemVer и **всё дерево** L0, а также **всё дерево** L2 побайтно прежние. Один инвариант — операция попадает только в реально раздельную область своего хранения. Испытательный проект — отдельное временное дерево с реальными файлами и кодом v2; это не текущий ISyncAI, не выделенный тест-агент и не установка выпуска.

| Решение | Основание и граница |
|---|---|
| Доверенная привязка из вызывающего кода: абсолютный рабочий каталог и выбранный относительный каталог профиля. В пробе `kit/base/registry.json`, `profiles/pilot/registry.json`, `.agent-contract/project/registry.json`. | Для каждого загруженного документа ровно один корень совпадает с привязкой. `area` и `roots` проверяются, но не выбирают путь записи. `scope` — применимость, не адрес файла. Нет поиска профиля по данным/соседним папкам. |
| Сначала непересечение заявленных корней, затем реальные каталоги и обычные файлы; не следовать ссылкам внутри рабочей зоны. | Пересечение привязок — `profile_root_conflict`. Символическая ссылка на корень или реестр, reparse-метка или несколько имён у одного файла реестра — `unsafe_path`. Отсутствующий файл — ошибка, не пустой старт; неверный `area` или отличный `roots` не переопределяет привязку. Область I/O проверяется на стабильном дереве с одним писателем, **не** через модель ACL, гонок замены пути, NTFS/junction или монтажных пространств. |
| Внутренние `status`, `plan_create`, `apply_create`: только создание одного синтетического `rule`/`draft` в выбранном L1. | План показывает добавление и переход ревизии, сам не пишет. Отдельный аргумент подтверждения связывается с этим планом; при записи план пересчитывается на заново прочитанном L1. Сценарий явно подтверждает тестовый план. Хеш — привязка, не удостоверение пользователя. Это технический порт под Ф2, не новый пользовательский язык, не готовый диалог/билет И‑110. |
| Ревизия и записи хранятся в одном JSON. Запись через временный файл рядом и `os.replace`, без сохранения промежуточной ревизии в другом документе. | Наблюдаем ровно один заменённый файл; при инъекции отказа замены старый файл и дерево остаются прежними. Это не доказательство сохранности при аварийном отключении или конкурентных писателях. Мы **не переносим** двухфайловый стенд И‑103 и CLI донора. |
| Независимое измерение тестом, а не только ответом метода записи. | Снимки байтов и состава всех трёх деревьев до/после, отдельный хеш синтетического манифеста L0 (наблюдаемое значение, не допуск установки), повторное чтение `status` и файла L1 новым вызовом. `0.2.0-dev.105` в фикстуре — SemVer для измерения, не опубликованный выпуск. |

**П2. До реализации.** В [CASES.json](CASES.json) фиксируются ожидаемые состояния и точные отказы. Положительные: read-only `status`, один `plan → confirm → apply → status`. Отрицательные: вложенность фактических каталогов L1 в L0/L2 (X01); чужая цель записи L0 (X02); несовпавшая декларация, чужая область, отсутствующий файл; физические алиасы; неподтверждённый или изменившийся дифф; отсутствующий локальный родитель; попытка сразу создать активную запись; отказ замены. Там, где отклонение уже известно, исправлять данные чтением нельзя.

**П3–П5. Критерий успеха / провала.** Код из checkout дважды не переиспользует состояние: П3 работает на свежих временных зонах из исходников checkout, П4 запускает тот же набор в новом интерпретаторе из ровно перечисленных файлов без Git, 0.1.36 и ISAI. Нужны все обязательные ID ровно один раз, точные значения/типы, совпавшие входы и наблюдения, отсутствие дополнительных файлов. На единственной записи разрешён только `profiles/pilot/registry.json`; во всех отказах и read-only шагах изменений нет. Отсутствие случая, неверный код, побочная запись или отличие копий блокируют приёмку. Результат донора не заменяет ни одной проверки: отдельная ссылка на уже принятый контроль, без нового нативного прогона 0.1.36.

**П6–П9.** Отчёт из измерений, финальная приёмка внутри печати, read-only повтор, страница, запись сверки и commit/push текущей ветки. Откат разработки — отмена коммита (все состояния пробы временные). Нет журнала решений, десяти регистраций и общей политики `no_change`/устаревших запросов И‑106, матрицы A1–A4 И‑107, установки или регистрации/активации `R-2`. Не меняем схему И‑104, `.isai/`, исторические печати, пользовательские каталоги и опубликованные версии.
