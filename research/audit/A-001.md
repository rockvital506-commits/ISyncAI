# A-001 · Аудит машины состояний по всем пройденным итерациям

18 ноября 2026. Проверяемый выпуск — **0.1.26** (последний сданный). Прогон — `research/audit/state_audit.py`,
результат — `research/audit/AUDIT-0.1.26.json`. Всё измерено опубликованной командой в отдельном процессе;
внутренние функции не вызывались.

## Что такое машина состояний в этом комплекте

| Элемент | Значение |
|---|---|
| состояния записи | `draft`, `active`, `suspended`, `revoked` |
| переходы | `draft → active`, `draft → revoked`, `active → suspended`, `active → revoked`, `suspended → active`, `suspended → revoked` |
| терминальное | `revoked` — выхода нет |
| контракт | состояние контракта задаёт применимость всех его записей без переписывания детей |
| проект | `retired` — отдельный флаг, не состояние записи |
| чтения | `list` (действующий набор), `metrics` (счёт), `due` (сроки), `status` (`health`) |

## 1. Матрица переходов — измерена целиком

32 проверки: 4 × 4 пары для контракта и для правила. Эталон — 6 разрешённых пар, 10 запрещённых.

| Из \ В | draft | active | suspended | revoked |
|---|---|---|---|---|
| **draft** | запрещён | разрешён | запрещён | разрешён |
| **active** | запрещён | запрещён | разрешён | разрешён |
| **suspended** | запрещён | разрешён | запрещён | разрешён |
| **revoked** | запрещён | запрещён | запрещён | запрещён |

Факт: `matrix_gaps: []` — расхождений с эталоном нет ни для контракта, ни для правила. Отказ приходит кодом
`transition`, текст называет «откуда» и «куда».

## 2. Влияние состояний на чтения — измерено

| Сценарий | `list.active` | `metrics.active` | `metrics.hidden` | `metrics.noise` | `metrics.revoked` |
|---|---|---|---|---|---|
| контракт active, правило active | 1 | 1 | 0 | 0 | 0 |
| контракт suspended | 0 | 0 | **1** | 0 | 0 |
| правило suspended | 0 | 0 | 0 | **1** | 0 |
| контракт revoked | 0 | 0 | **1** | 0 | **1** |
| проект retired | 0 | 0 | **1** | 0 | 0 |

Инварианты счёта сошлись: сумма состояний равна числу записей; `active` и `hidden` не больше числа
`active`-записей; `noise` не больше `draft + suspended`; `revoked` равен числу `revoked`.

## 3. Находки

### A1. Дефект: под отменённым контрактом создаётся новая запись

Факт: `create` правила под контрактом в состоянии `revoked` возвращает `ok` (план разрешает запись).

Почему это дефект: `revoked` терминально по объявлению («отмена терминальна»), но ветка под ним принимает
новые записи. Такая запись не попадает в набор никогда, и участник узнаёт об этом только по `metrics.hidden`.

### A2. Дефект: `active`-запись создаётся под неактивным контрактом

Факт: `create` с `state: "active"` под контрактом `draft`, `suspended` и `revoked` — `ok`.

Почему это дефект: `active` означает «действует», а запись под неактивным контрактом не действует. Комплект
принимает противоречивые данные и потом объясняет их через `hidden` вместо того, чтобы отказать при вводе.

### A3. Дефект: активация обходит A2

Факт: `transition` `draft → active` для записи под неактивным контрактом (`draft`, `suspended`, `revoked`) — `ok`.

Почему это дефект: даже если запретить A2 на `create`, тот же результат достигается двумя шагами.

### A4. Недостаток: `due` не называет состояние

Факт: элементы `due` — `id, title, scope, owner, review_by, never, overdue`; поля `state` нет.

Почему это недостаток: просроченный `draft` и просроченное действующее правило неразличимы. Срок проверки —
это работа, а работа над черновиком и над действующим правилом разная.

### A5. Недостаток: `hidden` не делит причину

Факт: `hidden` — `count`, `bytes`, `ids`, `why`; `by_reason` нет.

Почему это недостаток: скрытое бывает трёх разных сортов — контракт `draft`, `suspended`, `revoked`, плюс
`retired` проекта. Одна строка «почему» заставляет участника выяснять сорт вручную.

### A6. Покрытие: матрица переходов не проверялась ни тестами, ни стендом

Факт: в испытаниях комплекта 13 переходов (`active` 7, `revoked` 4, `suspended` 2), парная проверка всех
16 пар отсутствует; в пилоте переходы проверяются сценарно (L4D, L4M), а не матрицей.

Почему это важно: A1–A3 существовали с самого появления состояний и не были замечены именно потому, что
проверялись сценарии, а не таблица.

### A7. Вне области: корпуса и журналы состояний не задействуют

Факт: `pairs_cli.py`, `pairs_journals.py`, `corpus.py` работают с наблюдениями (`environment`), а не с
реестром правил; `suspended`/`revoked` в них не встречаются.

Почему это не дефект: корпуса проверяют правило тождества события, а не машину состояний. Отмечаю, чтобы не
искать там покрытие, которого не должно быть.

### A8. Недостаток: `hidden` при `target` считает «вне области» скрытым

Если задать `target`, `active` сужается по области, а `hidden` — как разность `active`-записей и набора —
тогда правило в действующем контракте, но вне области, попадает в «скрытое контрактом». Это смешивает два
разных факта: «контракт не действует» и «запись вне области». Найдено при подготовке 0.1.27, проверено
на стенде: до правки `hidden.count` рос от сужения по `target`.

## 4. Что проверено и претензий не имеет

| Проверка | Результат |
|---|---|
| `purge` только после `revoked` и с `allow_delete` | `revoked` → `ok`; `draft`/`active`/`suspended` → `delete` |
| `purge` контракта с детьми | отказ `parent`, каскад запрещён |
| `edit` отменённой записи | отказ `edit` |
| `review` отменённой записи | отказ `review` |
| `due` не включает `revoked` | верно |
| `retired` проекта | `list` пуст, `status.health` = `retired` |
| счёт `metrics` | сходится с `list` и с числом записей |

## 5. Вытекающие последствия

| Что | Как закрывается |
|---|---|
| A1 | `create` под `revoked` контрактом — отказ `parent` с `{contract, state}` |
| A2, A3 | `active`-запись возможна только в `active` контракте: отказ `state` при `create` и при `transition` |
| A4 | `due` называет `state` каждой записи |
| A5 | `metrics.hidden.by_reason`: `parent_draft`, `parent_suspended`, `parent_revoked`, `retired` |
| A8 | `hidden` считается без сужения по `target`: запись вне области не скрыта контрактом |
| A6 | испытания `X68`, `X69` и уровень стенда **L4T** — матрица 32 пар, три запрета входа, `due.state` и `by_reason` |
| данные | схема не ужесточается: уже существующие записи под неактивным контрактом читаются, `hidden` их показывает |

## 7. Вывод

Машина состояний в комплекте **исполняется верно там, где она проверяется**: 32 перехода совпадают с
эталоном, чтения считают правильно, `purge` и `retired` ведут себя как объявлено. Дыры — на **входе**:
новые записи и активация не спрашивают состояние контракта, поэтому в реестре может появиться `active`
запись, которая не действует, или запись в мёртвой ветке. Это не ошибка счёта, а ошибка допуска.

Закрыто выпуском **0.1.27** (И‑047 «Аудит: контур машины состояний»): отказы на входе (`parent`, `state`),
`due.state`, `metrics.hidden.by_reason`, `hidden` без сужения по `target`, испытания `X68`/`X69`, уровень
стенда `L4T` (32 пары, 0 расхождений). Схема не ужесточена — старые данные читаются, а расхождение
показывается, а не прячется.
