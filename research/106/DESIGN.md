# И‑106 · Ф1 · P0 — десять регистраций L1 и журнал решений

**П0. Сверка до работы.** Чистая ветка от `8e03563`, [стратегия v1.7](../STRATEGY.md), §1.5, §3.1–3.3, Ф1 и §5. [И‑105](../105/ACCEPTANCE.json) уже пишет в раздельный L1, но не хранит историю и не различает повтор свежего запроса и подачу старого плана. [Фикстура X03](../strategy/pre-104/SCHEMA-CASES.json) задаёт оба исхода; берём синтетическое `rule` вместо `R-2`. [Стенд И‑103](../103/VERSION-EVIDENCE.json) показал методику `0 → 10`, не испытал рабочий Kit. Опровержения порядка фаз или критерия И‑106 до реализации нет.

**П1. Гипотеза.** Десять отдельных подтверждённых `create` оставят десять согласованных решений с `profile_revision` от 1 до 10. На всех одиннадцати точках, включая старт, неизменны SemVer, весь состав и байты дерева L0, SHA‑256 тестового манифеста и дерево L2. Чтение, предпросмотр, `no_change` и отказы не двигают ни ревизию, ни журнал. Один инвариант: история принятых изменений L1 согласована с его счётчиком, не превращаясь в версию продукта.

| Решение | Основание и граница |
|---|---|
| Использовать тот же внутренний `plan_create` / `apply_create` и файловую привязку И‑105. | В каждой операции новое подтверждение тестового диффа, один `rule`/`draft` под существующим контрактом, свежая загрузка с диска. Не пользовательский CLI, не автоматика согласия, не изменение `R-2`. |
| Один файл L1 с закрытым контейнером `profile_format: 1`, внутри неизменный `registry` v2 и `journal` (`base_revision`, `decisions`). | Правило, счётчик и решение записываются **одной** заменой. Отдельный JSONL потребовал бы транзакции между файлами либо оставлял бы расхождение при отказе. Номер контейнера — формат, не SemVer. Обычный v2 L1 из И‑105 читается без записи; прежняя ревизия становится основанием наблюдаемой истории, прошлые записи не выдумываются. При первом принятом изменении контейнер пишется в тот же файл. L0/L2 и форма схемы v2 не меняются. |
| Журнал фиксирует только принятые `create`: `operation`, `entry_id`, `profile_revision` и `entry_sha256` канонической записи. | Связь решения с записью, её `basis` и `criterion` без дублирования текста. Ревизии последовательны и соответствуют добавленному хвосту записей; несовпадение блокирует чтение рабочего состояния и запись. Нет путей машины, билетов, временных меток или тела запроса. Журнал локальный; для будущего переноса предназначен отдельно проверенный `registry`, а не весь файл. Не защищённый аудит, не подпись, не глобальное упорядочивание между копиями. |
| Идентичный свежий `create` по тому же ID даёт `no_change`: без билета, без записи. Занятый ID с другим валидным содержанием — `entry_exists`; старый подтверждённый план — `stale_revision`, даже если правило уже создано. | Не путать новую проверку текущего состояния с повтором согласия. При равной ревизии изменение байтов всё равно делает прежний план неприменимым (`plan_mismatch`); сравнивается пересчитанный план, а не один номер. Наполнение/конфликты по `key` и разрешения других операций — И‑107/И‑116. |
| Инъекция отказа непосредственно на единственной замене. | Перед заменой проверяется, что в подготовленных байтах уже вместе реестр и следующая строка журнала. После отказа (`write_failed`) прежние ревизия, запись и журнал сохранены, временного файла нет. Не модель отключения питания, конкурентной записи или прав NTFS. |

**П2. До реализации.** [CASES.json](CASES.json) фиксирует старт, десять последовательных записей, два свежих повтора и чтение старого формата с ненулевой ревизией. Отдельно — устаревший план для ещё не созданного ID, повтор использованного билета, дрейф байтов при прежней ревизии, занятый ID, отказ замены и три повреждения журнала. Для каждой принятой записи независимый тест сравнивает байты/состав корней, планы, фактически перечитанный реестр, всю историю, поля `status` и единственный вызов замены. Состояние после десятой регистрации сохраняется как свидетельство, не как пользовательский профиль.

**П3–П5. Успех / провал.** Реальное временное рабочее дерево с кодом из checkout; новый процесс из копии только названных входов создаёт свои рабочие файлы. Ни один прогон не зависит от 0.1.36 или ISAI. Точный переход `0 → … → 10`, ровно десять решений, одиннадцать разных digest файла L1, неизменные L0/L2 на каждой точке; все обязательные ID ровно по одному с точными исходами, наблюдения совпали, исходники неизменны. Неверный тип/код, пропуск, дополнительная строка журнала или сохранение половины перехода блокирует приёмку. Донора вновь не запускаем, его прежний контроль не прибавляет целевых `pass`.

**П6–П9.** Отчёт с критериями, машинные результаты и приёмка внутри детерминированной печати, read-only повтор, страница, сверка и commit/push текущей ветки. Откат разработки — отменить коммит; временные профили удаляет тест, это не миграция рабочих данных. Вне работ: И‑107, журнал применения правил в L2, полноценный пользовательский цикл, промоушен/активация, миграция/восстановление, живые среды и правки ISAI/прошлых печатей.
