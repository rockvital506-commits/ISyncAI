# И‑104 · Ф1 · P0 — замысел до прогона

**П0. Сверка.** [Стратегия v1.5](../STRATEGY.md), §1.5–1.7, P2/P6, A1–A4, вход И‑104 и [ретроспектива](../strategy/pre-104/RETROSPECTIVE.md), начало от `0418089`. В дереве нет реализации v2 или действующего L1. Предшественник И‑103 проверил методику и стенд; не наследуем его двухфайловую запись. A1–A4, состав P0 и порядок фаз остаются прежними.

**П1. Гипотеза.** Одну поверхность — контракт данных — можно определить как чистую проверку JSON: произвольное допустимое содержание L0/L1/L2 проходит без 0.1.36 и ISAI, некорректное отклоняется без правки данных. Аналогии: системная платформа задаёт форму L0, переносимая политика L1 не становится системным разрешением, L2 хранит договоры проекта. Адаптер, реальные права и sysprep-перенос не входят в этот прогон.

| Выбор | Обоснование и граница |
|---|---|
| Один исполнимый контракт `kit/base/schema_v2.py` на Python ≥3.10, stdlib, и описательная спецификация | Внешний JSON Schema-движок не решил бы поиск родителя или вложенность `scope` сам по себе. Не поддерживаем параллельно две машинные схемы и не строим собственный универсальный движок. Формат входа — JSON, валидатор пригоден без Git и доноров. |
| Оболочка `schema_version: 2`, `area`, `roots`, `entries`; у L0 `release_version`, у L1/L2 свой `revision` | Формат, версия системного выпуска и счётчики независимы. `area` и счётчик принадлежат документу, не дублируются в его строках. `authority` записи (`system_release` / `profile_owner` / `project_owner`) — тип декларации, совместимый с областью, не удостоверение или право. При известной области загрузки её передаёт вызывающий код отдельно. |
| `id`, `kind`, `state`, `authority`, `parent`, `scope`, `title`, `text`, `basis`, `criterion`; `key`/`value` — только парой | ID — непрозрачный токен, не префикс прав. Родитель разрешается в том же документе: нет скрытой зависимости от другого слоя. У контракта `parent: null`, у дочерней записи — ID существующего `contract` с охватывающим `scope`. Для исторических ссылок И‑131 должен показать сохранение смысла и идентичности либо отказ, не тайное переподчинение. |
| `roots` и `scope` — разные относительные пути; для `scope` допустима точка | Форма лексическая и переносимая: `/`, не абсолютный, без пустых, `.`/`..` и неоднозначных компонентов. Сравнение `scope` покомпонентное и точное; разные регистры не расширяют область. Явно совместно переданные декларации корней проверяются на совпадение/вложенность, консервативно без учёта регистра. Никакой проверки фактической ФС, ACL, junction, ссылок или области записи. |
| Чтение → форма → связи; одна точная диагностика `stage/code/path` | Дубликат члена JSON не должен теряться при чтении; `true`, `1`, `1.0` и `"1"` не взаимозаменяемы. Не заменяем отсутствующее поле значением по умолчанию, не нормализуем ввод молча. Операционные коды A1–A4 проверяются отдельно в И‑107. |

**П2. Замороженный план испытаний.** [CASES.json](CASES.json) разворачивает все V01–V02 и N01–N12 из [подготовительного корпуса](../strategy/pre-104/SCHEMA-CASES.json) в исполняемые случаи. Добавлены контрпримеры неправильной известной области/полномочий, двух шкал версий, объявления корней, внешнего родителя и неоднозначного JSON. Для каждой мутации задана причина и путь до реализации. `R-2` остаётся `draft`; в v2 проверяется тело, не ссылка `text_file` и не реальность активации. X/B остаются будущими испытаниями.

**П3–П5. Критерий и провал.** Целевой прогон из checkout и отдельный процесс из временного дерева ровно из перечисленных входов (без ZIP донора, ISAI и харнесса). Нужны все обязательные ID ровно по одному разу в каждой копии, с точной диагностикой для отрицаний и неизменными входами. Любой пропуск, лишний/повторный ID, неверный тип/код/путь, изменение входа или расхождение копий блокирует приёмку. Параллельные счётчики не складываются: отдельно проверка драйвера и контроль на закреплённом 0.1.36 (`check_preparation.py` против сохранённого `EVIDENCE.json`); этот контроль не добавляет ни одного целевого `pass`.

**П6–П9.** Отчёт из проверенных наблюдений; приёмка и отчёт входят в детерминированную печать, повтор сравнивает сохранённое без записи, страница строится из тех же результатов; после сверки — commit/push. Изменённый вход требует новой печати. Откат: отменить коммит И‑104; пользовательские реестры, `.isai/`, донорский ZIP и исторические снимки остаются нетронутыми.
