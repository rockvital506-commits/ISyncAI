# Справочник механизма • 0.1.0 / схема 1

Это описание доступных операций, а не пользовательский протокол взаимодействия. Реестр изначально пуст. Образцы данных и проверки находятся только в отдельном тестовом комплекте. Комплект рассчитан на одного владельца и последовательные записи; библиотек, плагинов, сети, Git, фоновых процессов и учётных записей для файловых операций не требует.

## Кто что изменяет

Владелец принимает решения. Сопровождающий базы готовит новый выпуск; сопровождающий проекта отвечает за локальную копию. В личном использовании это может быть один человек. Агент может предложить формулировку, объяснить изменение, использовать ранее полученное конкретное согласие и исполнить одобренный план. Проверяющий фиксирует наблюдение, а не превращает догадку в факт. Пользовательские требования не могут расширять разрешения редактора, ОС или корпоративных политик.

База — декларативные данные из выпуска; `state.json` — локальные записи, решения, состояние входа и привязка базы; `checks.json` — наблюдения. История решений хранит метаданные, а не переписку и не второй реестр. Ничего из проектной области по умолчанию не экспортируется. Дата, ревизия проекта, версия записи, схемы, базы и адаптера отражают разные вещи. Версия расширения, редактор, модель и режим относятся к конкретному наблюдению.

## Интерфейс для агента и автоматизации

Форма вызова утилиты: `python -I -B kit/tools/contract.py --lab <абсолютный-путь> --project <путь-относительно-lab> <команда>`. Для `list` допустим `--target <относительный-путь>`. Угловые скобки — места для значений, не часть имени. `--lab` и существующая папка проекта задают границы, ничего не ищется по диску. `--project` не требуется для `updates` и публикации. Утилита использует только стандартную библиотеку Python 3.11 и новее; наличие Python на отдельном ПК не предполагается. Запуск только из отдельно одобренного комплекта. Никаких скриптов из устанавливаемых данных.

Результат — UTF-8 JSON. Читающие команды: `status`, `list`, `history`, `operations`, `pending`, `updates`. Не создают файлов или блокировок. `updates` перечисляет только локальные кандидаты `releases/X.Y.Z`; показанный отпечаток не служит подтверждением источника. `session` принимает в UTF-8 JSON по стандартному вводу `kind` (`temporary`, `proposal`, `hypothesis`) и `text`, ничего не записывает. Показ действующего набора исключает черновики, приостановленные, отменённые и записи неактивного родителя. Без `--target` перечисляются все действующие области; это не означает, что они применяются одновременно ко всем файлам.

**Две разные операции:** `plan` читает объект запроса из стандартного ввода, возвращает `request`, `ticket`, точную разницу по файлам, их отпечатки и примечания. `apply` читает ровно `{"request": …, "ticket": …}` от конкретного просмотренного плана. Предпросмотр не пишет даже резервные копии. Билет связан с корнем проекта, версией движка, входными данными, временем и точными результатами. Это проверка актуальности, а не подпись владельца. Получение билета не означает согласия человека. Агент не должен одобрять сам себя. При изменении плана, входных файлов или требуемых прав нужно другое согласие. Код возврата 0 означает выполненную команду, не соблюдение правил моделью. Ошибки, частичное восстановление и состояние `attention`/`partial` возвращают 2 и диагностический объект. При ошибке ввода/вывода после начала записи проверяется `pending`, а не предполагается успех.

| Намерение | `op` и поля запроса к `plan` |
|---|---|
| Развернуть чистую базу или перенести её в другой проект | `install`, `package: releases/X.Y.Z`, `pin` (одобренный SHA-256 байтов манифеста). Только перечисленные базовые файлы, пустые проектные записи и результаты. Нет автоматического подключения агента. |
| Подключить текущего агента | `connect`. Создаёт только корневой `AGENTS.md` из шаблона; вторая попытка не создаёт разницы или ревизии. Занятый чужой вход не читается для присвоения и не заменяется. |
| Создать контракт или принадлежащую ему запись | `create`: `kind`, `title`, `scope`, `text`, `basis`, `criterion`, `reason`; необязательно `state` (`draft` по умолчанию или явно `active`), `key`, `value`. У записи нужен `contract` (ID родителя), у самого контракта родителя нет. Вид — `contract`, `rule`, `constraint`, `protocol` или `preference`. Названия видов не создают сущностей. |
| Изменить формулировку или область | `edit`, `id`, `reason`, объект `fields` (только `title`, `scope`, `text`, `basis`, `criterion`, `key`, `value`). Старый и новый текст видны в разнице. Если реально ничего не изменилось — нет ревизии. |
| Активировать, приостановить, возобновить, отменить | `transition`, `id`, `to`, `reason`. Переходы: draft → active/revoked; active → suspended/revoked; suspended → active/revoked. Отмена терминальна. Смена состояния контракта влияет на применимость всех его записей без переписывания детей. |
| Физически удалить запись | `purge`, `id`, `reason`, `allow_delete: true`. Только отменённая запись, без каскада; ID при обычном продолжении истории не переиспользуется. Удаление из текущего файла не стирает историю, копии и внешние журналы. |
| Обновить базу или согласовать локальную правку базы | `update`, `package`, `pin`; при конфликте — необязательный объект `resolutions` с возвращёнными ключами конфликта и значениями `local`/`incoming`. |
| Изменить формат проекта | `migrate`, `reason`. Поддерживаемый вход описан ниже. |
| Зафиксировать наблюдение | `record_check`, `observation`: `case`, `level` (1–5), `conditions`, `expected`, `actual`, `status`, `evidence`, `limits`, `environment`. Среда: `os`, `editor`, `editor_version`, `extension`, `extension_version`, `mode`, `model`, `profile`, `permissions`. Неизвестные значения так и обозначаются. |
| Отключить вход или вывести копию из эксплуатации | `disconnect` или `retire`. Для удаления принадлежащего системе неизменённого входа нужно `allow_delete: true`. Реестр и история остаются; у выведенной из эксплуатации копии нет действующих правил. |
| Восстановить незавершённую операцию / откатить ошибочное завершённое изменение | `restore` / `undo`, `tx` из `pending`/`operations`; отдельное `allow_delete: true` только для согласованного удаления созданных операцией файлов. Сначала такой же просмотр, затем подтверждение именно этого билета. |
| Подготовить новый выпуск (роль сопровождающего) | `publish`, `version` (новый X.Y.Z), `origin`, `adapter_version` (положительное целое). Берёт только разрешённые данные из `kit/base`, строит манифест, публикует в ранее не существующий `releases/<версия>`. Не изменяет прежние выпуски; агентский вход или код из проекта источником публикации не являются. |

## Реестр и конфликт

ID выдаётся утилитой (`P-1`, `P-2`, …); `B-…` принадлежат выпускающей стороне. Поля записи: устойчивый ID, вид, родитель, название, точный текст, основание, критерий проверки, состояние, относительная область, номер ревизии записи, дата UTC и причина. Исходная область `.` — весь проект; `src` охватывает `src` и потомков, но не `src2`. Сопоставление областей не зависит от регистра, разделитель `/`; абсолютные пути и выход наверх запрещены. Область ребёнка должна быть внутри области родителя.

Объективно сравнимому требованию можно задать пару `key` + `value`. Одинаковый ключ, разные значения и пересечение активных областей дают конфликт: выводятся обе формулировки и области, запись не производится. Возможные решения: сузить область, уточнить условие, изменить предложение, приостановить одну из записей или отказаться от изменения. Не все естественно-языковые противоречия формализуемы. `key` не является разрешением инструмента. Не распознаём намерение эвристикой «всегда = записать»: посредник в чате сначала отделяет конкретную постоянную просьбу от разовой, предложения и гипотезы. Если неясно — спрашивает, а не записывает.

## Сопровождение и перенос

Обновление требует трёх экземпляров: точных байтов ранее одобренного выпуска (по пину проекта), локальной базы и нового выпуска с независимо одобренным пином. URL, имя, подпись текстом или хеш с того же неподтверждённого носителя не доказывают происхождение. При отсутствии общего предка — отказ, а не имитация слияния. Независимые изменения в разных записях сливаются по ID; неоднозначное изменение одного ID или одного документа требует решения. Удаление записи учитывается как изменение. Эффективный результат снова валидируется на схему, принадлежность и конфликты с проектным слоем. Отпечатки локально установленного результата хранятся отдельно от исходных из манифеста. Переиспользование номера выпуска с другими байтами и автоматическое понижение запрещены.

В проект Б устанавливается одобренный выпуск, не дерево проекта А. Пять файлов данных + манифест — закрытый список. Не переносятся история/правила/проверки А, служебные копии, Git, профили, права, службы, расширения или аккаунты. Вход за пределами `.agent-contract` подключается в Б отдельно с учётом существующих инструкций. Статус `created` относится к файлу, не к загрузке. При смене проекта/профиля/среды — новый сеанс, новое наблюдение. Для дополнительных клиентов их собственные форматы и режимы проверяются отдельно; автоматической записи в конфигурации Copilot, Kilo, Cursor, Claude Code и Antigravity нет.

Схема 1 не угадывает будущие схемы. Для воспроизводимой проверки миграции определён **синтетический обменный формат 0**, не заявляемый историческим выпуском: ключ проекта `project_revision` вместо `revision`, `status` вместо `state` у каждой локальной записи, `schema_version: 0`. Все остальные поля сохранены. План 0 → 1 показывает точное переименование и запись решения. Неоднозначные/неизвестные поля или версия — отказ без записи. Любая следующая несовместимая схема требует явного преобразования, проверок и возможности восстановления.

## Надёжность и границы

Перед записью берётся межпроцессная блокировка только для сотрудничающих экземпляров утилиты; повторно сравниваются входные байты. До первой замены публикуется журнал `local/ops/<id>/plan.json` с до/после-отпечатками и проверенными исходными байтами в `before/`. Отсутствовавший до записи файл отмечен `null`. Отдельные файлы заменяются из временного файла в том же каталоге. Сразу после прерывания возможны старые и новые файлы одновременно. `pending` и `status` способны показать незавершённость без чтения полусобранной базы. Восстановление классифицирует каждую цель: прежняя, новая, чужая, требуется разрешение на удаление. Разрешённые байты возвращаются, посторонние сохраняются, операция остаётся незавершённой до разрешения всех путей. Завершённый ошибочный шаг откатывается только отдельным `undo` при точном постсостоянии его целей. Откат сам защищён журналом. Имена исчезнувших до операции файлов удаляются только отдельным разрешением. Пустые служебные каталоги и журналы намеренно не очищаются.

Это не транзакционная файловая система, архив секретов или неизменяемый аудит. Восстанавливаются байты обычных файлов, не ACL, владельцы, альтернативные потоки и произвольные метаданные. Проверяются компоненты путей, специальные файлы, hard links файлов, symlink/reparse points; неопределённое состояние останавливает запись. Требуется контролируемый локальный каталог одного владельца, не недоверенная конкурентно меняющаяся иерархия и не сетевая/синхронизируемая папка. Перенос активного журнала в другую папку как способ восстановления не поддерживается. Дубликаты ключей JSON, неизвестные поля и файлы данных сверх 2 МиБ не интерпретируются наугад. База и копии должны быть без секретов. При случайном попадании секрета — не цитировать, отдельно рассмотреть отзыв, замену и согласованный план очистки внешних копий.

## Проверки и показания

Статусы: `pass`, `fail`, `not run`, `inconclusive`. Структура файла (1), обнаружение входа клиентом (2), загрузка/наблюдаемое чтение канонического текста (3), выполнение требования (4) и повторения в независимых сеансах (5) — разные свидетельства. Статус на одном уровне не переносится на следующий. После изменения редактора, расширения, профиля, модели, базы или важного правила нужна новая запись, а не перенос старого успеха. В личном пилоте сравниваются одинаковые задачи с контрактом и без, при сопоставимых условиях; оцениваются нарушения, ложные срабатывания, ручные исправления, время и стоимость, если она известна. Метка для контрольной задачи не подсказывается в вопросе. Эти результаты не доказывают причинность или безопасность.

Покрытие комплекта: T01 состав, T02 ссылки, T03 уникальность ID, T04 состояния/совместимость, T05 добавление, T06 изменение, T07 приостановка/возобновление, T08 отмена/удаление, T09 временное намерение, T10 конфликты, T11 повторное подключение, T12 новый сеанс, T13 перенос, T14 отсутствие примеси данных А, T15 обновление, T16 прерывание, T17 восстановление. Для T12 свежий процесс утилиты — проверка чтения с диска, не сеанс Copilot/Kilo. При отсутствии реальной среды её часть T12 имеет статус `not run`. Технические права остаются у ОС и клиента. Фоновый мониторинг, самообновление и автоматическая передача куда-либо отсутствуют.
