## 00. Как пользоваться файлом

- Перед итерацией: прочитать §2, §3, нужную фазу (§4), протокол (§5).
- После итерации: заполнить запись сверки (§10). Расхождение → правка файла в том же коммите.
- Файл читается первым в каждой сессии; он же — вход для нового агента.
- Машинные спутники: `research/strategy/BASELINE.json` (baseline выпуска), `research/strategy/SYNC-LOG.md` (журнал в читаемом виде).

## 1. Рамка

1.1 Что строим: самостоятельная переносимая и поддерживаемая система контрактов взаимодействия (правила, протоколы, реестры поведенческих и конституционных сущностей проекта), управляемая обычной фразой пользователя.

1.2 Среды: **Arena Agent Mode** (GitHub), **Kilo** (VS Code), **GitHub Copilot** (VS Code). Claude Code / Cursor / Antigravity — заглушки (`status: stub`, причина названа).

1.3 Вне контекста: линия AgentContractKitISAIEdition (итерации 057–069 отменены), ядро ISAI (`.isai/`), любые правки чужих проектов.

1.4 Владелец: пользователь. Агент исполняет, показывает план и не решает за владельца.

1.5 Раскладка 0.1.36 **не меняется**: `kit/base/*`, `kit/tools/contract.py`, `kit/tests/`, `releases/`, `project/{state,checks}.json`, `local/`. Расширяем, не переписываем.

1.6 Место артефактов итерации: `research/<NNN>/{REPORT.md,ACCEPTANCE.json,Итерация-<NNN>.html}`; стратегия — `research/STRATEGY.md` + `research/strategy/`. Текстовые артефакты — в git; крупные zip — только с записью хеша в отчёте.

## 3. Модель

### 3.1 Области и адреса

```
L0: kit/base/{manifest,START,PROTOCOL,schema,rules,entry}   roots = ["kit"]
L1: profiles/<имя>/{profile.json,rules.json}                roots = ["profiles"]   revision: N
L2: .agent-contract/project/{state.json,checks.json} + журнал  roots = [".agent-contract"]
```

- **A1**: roots областей не пересекаются (иначе `profile_root_conflict`).
- **A2**: запись в L0 невозможна никакой операцией уровня L1/L2 (`system_immutable`).
- **A3**: молчаливый победитель запрещён; при противоречии — отчёт о конфликте.
- **A4** (уточнено в И‑101 по факту 0.1.36): запись вида `rule|constraint|protocol|preference` **обязана** принадлежать существующему `contract` и не выходить за его `scope`; контракт родителя не имеет. Минимальный `create` = 2 шага.

### 3.2 Версии

- semver — только L0 (продукт). Правила профиля semver не двигают.
- `revision` — L1 (монотонно, при каждой мутации). `digest` — артефакт/пакет. `transaction` — идентификатор записи.
- Подпись опциональна, но её наличие/отсутствие объявляется (`unsigned`).

### 3.3 Операции

Вход — карточка; выход — план + билет; запись только по `apply`.

Существуют в 0.1.36 (15): `install`, `connect`, `disconnect`, `create`, `edit`, `transition`, `purge`, `review`, `record_check`, `merge`, `migrate`, `update`, `fix`, `retire`, `calibrate_answer`.
Добавляются программой: `promote`, `simulate`, `bundle`, `bundle_verify`, `guard`, `prompt` (компилятор карточки).

Команды CLI в 0.1.36 — 26 (см. `BASELINE.json`), в том числе `plan`, `apply`, `status`, `list`, `history`, `adapter`, `brief`, `updates`, `pending`, `operations`, `inventory`, `verify`.

### 3.4 Коды отказа (каждый обязан иметь тест)

`promote_unverified` · `project_specific` · `profile_root_conflict` · `system_immutable` · `bundle_incomplete` · `digest_mismatch` · `unsigned` · `simulation_failed` · `violation` · `parent` (A4) · `adapter_unknown` (сейчас: arena) · `foreign_entry` · `unknown_version` · `missing_params` — не отказ, а вопрос.

### 3.5 Сохраняется из 0.1.36

`TYPES = contract|rule|constraint|protocol|preference`; ID `B-` (база) / `P-` (проект), в программе добавляются `S-` (система) / `R-` (переносимый реестр); `TRANSITIONS draft→active→suspended/revoked` + `purge` только после `revoked` и `allow_delete`.

## 6. Приёмка и метрики

6.1 Итерация принимается при: 0 fail; оба прогона (П3, П4); отчёт с basis; печать; страница; коммит; запись сверки.
6.2 Фаза принимается при: DoD фазы + отсутствие открытых дефектов P0.
6.3 Метрики продукта: доля пройденных тестов; нарушений правил на 100 задач; ложных срабатываний; уточняющих вопросов на операцию; ручных правок; проблем после смены среды.
6.4 Метрики стратегии: доля итераций, потребовавших переупорядочивания (цель < 20 %); доля допущений, опровергнутых фактом (цель < 30 %); возвраты на фазу.

## 7. Правила сверки и синхронизации

7.1 Менять файл можно только по факту (тест, прогон, имитация, источник), не по мнению.
7.2 Каждая правка: запись в журнал (§10) + повышение версии в заголовке (v1.1 → v1.2).
7.3 Остановка и запрос подтверждения пользователя обязательны, если правка меняет: состав P0, порядок фаз, определение «условно пригодный», инварианты A1–A4.
7.4 Удаление итерации допустимо только с записью: какой инвариант теперь не доказывается и где доказывается вместо неё.
