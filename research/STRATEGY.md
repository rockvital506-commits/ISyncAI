1.6 Место артефактов итерации: `research/<NNN>/{REPORT.md,ACCEPTANCE.json,Итерация-<NNN>.html}`; стратегия — `research/STRATEGY.md` + `research/strategy/`. Текстовые артефакты — в git; крупные zip — только с записью хеша в отчёте.

## 3. Модель

### 3.1 Области и адреса

```
L0: kit/base/{manifest,START,PROTOCOL,schema,rules,entry}   roots = ["kit"]
L1: profiles/<имя>/{profile.json,rules.json}                roots = ["profiles"]   revision: N
L2: .agent-contract/project/{state.json,checks.json} + журнал  roots = [".agent-contract"]
```

- **A1**: roots областей не пересекаются (иначе `profile_root_conflict`).
- **A2**: запись в L0 невозможна никакой операцией уровня L1/L2 (`system_immutable`).
- **A3**: молчаливый победитель запрещён; при противоречии — отчёт о конфликте.
- **A4** (уточнено в И‑101 по факту 0.1.36): запись вида `rule|constraint|protocol|preference` **обязана** принадлежать существующему `contract` и не выходить за его `scope`; контракт родителя не имеет. Минимальный `create` = 2 шага.

### 3.2 Версии

- SemVer — только L0 (продукт). Изменения реестров не выпускают новый L0. SHA‑256 ZIP, pin манифеста и подпись — разные свидетельства; подпись опциональна, отсутствие объявляется (`unsigned`).
- `revision` — счётчик истории L1: +1 только при принятой мутации; чтение, предварительный план, отказ и `no_change` не двигают его. Git-коммит не является ревизией профиля.
- У L2 нет продуктовой версии. Нативный `status.project_revision` — счётчик проекта; `base.version` ссылается на L0, `schema_version` задаёт формат, `transaction` идентифицирует операцию. Не подменять ими ревизию профиля.
- Детали и границы доказательства: [версии](strategy/VERSIONING.md), [матрица совместимости](strategy/COMPATIBILITY.json), [политика Git](strategy/GIT-POLICY.md). Прямой кандидат на `0.2.0` — здоровый `0.1.36` со схемой 1; это не результат миграции. `compat --old` проверяется на реализации в И‑131.

### 3.3 Операции

Вход — карточка; выход — план + билет; запись только по `apply`.

Существуют в 0.1.36 (15): `install`, `connect`, `disconnect`, `create`, `edit`, `transition`, `purge`, `review`, `record_check`, `merge`, `migrate`, `update`, `fix`, `retire`, `calibrate_answer`.
Добавляются программой: `promote`, `simulate`, `bundle`, `bundle_verify`, `guard`, `prompt` (компилятор карточки).

Команды CLI в 0.1.36 — 26 (см. `BASELINE.json`), в том числе `plan`, `apply`, `status`, `list`, `history`, `adapter`, `brief`, `updates`, `pending`, `operations`, `inventory`, `verify`.

### 3.4 Коды отказа (каждый обязан иметь тест)

`promote_unverified` · `project_specific` · `profile_root_conflict` · `system_immutable` · `bundle_incomplete` · `digest_mismatch` · `unsigned` · `simulation_failed` · `violation` · `parent` (A4) · `adapter_unknown` (сейчас: arena) · `foreign_entry` · `unknown_version` · `missing_params` — не отказ, а вопрос.

### 3.5 Сохраняется из 0.1.36

`TYPES = contract|rule|constraint|protocol|preference`; ID `B-` (база) / `P-` (проект), в программе добавляются `S-` (система) / `R-` (переносимый реестр); `TRANSITIONS draft→active→suspended/revoked` + `purge` только после `revoked` и `allow_delete`.

### 3.6 Протокол-кандидат для L1: пофазовое исполнение промптов

- **L0** задаёт системные границы и операции. **L1** может хранить согласованный переносимый `protocol` с родительским контрактом (A4): *как* строить и модерировать план. **L2** содержит параметры и решения конкретной работы; её ориентир — один проектный файл, здесь `research/STRATEGY.md`. Сам ориентир, его журнал и проектные данные не переходят в L1. Текст протокола не расширяет полномочия и не заменяет технические проверки.
- [Текст кандидата](strategy/pre-104/PHASED-PROMPT-PROTOCOL.md) и [обоснование, порядок внедрения и проверок](strategy/pre-104/ADDENDUM.md). Статус: **подготовлен, не зарегистрирован**. Действующий профиль возможен только через запрос владельца, валидацию/исправление, имитацию, сверку конфликтов и подтверждение конкретного плана в рамках Ф2–Ф3. Штатное применение и переносимость ещё не измерены.

| П5 | Приёмка прогонов: 0 fail; `not run` перечислены, объяснены и учтены отдельно от `pass`. Отсутствие результата не равно явному `null`. Вердикт П5 не заменяет П7–П9 | `ACCEPTANCE.json` |
| П6 | Отчёт с находками: подтвердилось / опровергнуто / новые ограничения / basis | `REPORT.md` |
| П7 | Печать итоговых входов и повтор: сверить сохранённый архив и манифест с повторной сборкой без перезаписи. Размер и хеш — только из сборки. Входы после печати не переписываются: правка → новая печать, повтор и страница | архив + `SEAL.json` + протокол повтора |
| П8 | Страница из приёмки, печати и повтора. Страница и данные о самой печати не являются её входами | `Итерация-<NNN>.html` |
| П9 | Сверка-после + commit/push: запись в журнал; при расхождении — правка стратегии в том же коммите | коммит `И-<NNN>: <тема> — <что доказано>` |

Шаг считается выполненным только при наличии артефакта; иначе статус «не выполнен».

## 6. Приёмка и метрики

6.1 Итерация принимается при: 0 fail; оба прогона (П3, П4); отчёт с basis и criterion; совпавший повтор печати; страница; запись сверки; commit/push.
6.2 Фаза принимается при: DoD фазы + отсутствие открытых дефектов P0.
6.3 Метрики продукта: доля пройденных тестов; нарушений правил на 100 задач; ложных срабатываний; уточняющих вопросов на операцию; ручных правок; проблем после смены среды.
6.4 Метрики стратегии: доля итераций, потребовавших переупорядочивания (цель < 20 %); доля допущений, опровергнутых фактом (цель < 30 %); возвраты на фазу.

## 7. Правила сверки и синхронизации

7.1 Менять файл можно только по факту (тест, прогон, имитация, источник), не по мнению.
7.2 Каждая правка: запись в журнал (§10) + повышение версии в заголовке.
7.3 Остановка и запрос подтверждения пользователя обязательны, если правка меняет: состав P0, порядок фаз, определение «условно пригодный», инварианты A1–A4.
7.4 Удаление итерации допустимо только с записью: какой инвариант теперь не доказывается и где доказывается вместо неё.
7.5 При сверке различаем совпадение, ошибку исполнения и опровержение плана. Даже при `fail`/`not run` записываем основание, критерий и затронутые шаги. Ошибка не повод ослаблять критерий; для опровергнутого плана показываем дифф и повторную проверку. Без изменения содержания не повышаем редакцию. Новые обязательства и границы не вводятся без решения владельца (в частности, §7.3).
