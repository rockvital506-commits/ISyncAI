# Харнесс итераций: запуск и формат `ITERATION.json`

Первый проверенный вход — И‑102, выпуск AgentContractKit 0.1.36. Харнесс использует только стандартную библиотеку Python 3.10+. Это не универсальный раннер для произвольных выпусков: новая раскладка, версия или набор проб требуют явной доработки и собственной приёмки.

Из корня репозитория:

```sh
python3 -B research/strategy/harness/run_iteration.py --spec research/102/ITERATION.json
```

- `--dry-run`: проверяет спецификацию и показывает порядок и проверки, без изменения файлов или запуска проб.
- `--verify-seal`: повторно собирает ZIP в памяти и сравнивает его с сохранённым ZIP и `SEAL.json`; ничего не пишет. Для исторической печати нужны **те же байты** входных файлов (например, распакованный снимок соответствующего коммита), а не актуальная версия `STRATEGY.md`.
- Коды возврата: `0` — успешно, `1` — отказ приёмки, повтора или прогона, `2` — неверная спецификация. `--dry-run` с rc 0 не означает приёмку.

**Граница доверия.** Использовать только доверенные спецификации и ZIP выпуска: инвентарь импортирует Python-код, а пробы выполняют CLI и тесты из ZIP. SHA-256 проверяется **до** распаковки/импорта. Он обнаруживает несовпадение байтов с закреплённым артефактом, но не подпись. Временные каталоги отделяют состояние, не являются песочницей для чужого кода.

## Поля спецификации

| Поле | Назначение |
|---|---|
| `id` | Три цифры; спецификация в `research/<id>/ITERATION.json`, результаты — рядом. |
| `title`, `phase`, `priority`, `date`, `branch` | Шапка отчёта и страницы. |
| `goal`, `hypothesis`, `success`, `failure`, `rollback` | Замысел, проверяемый результат и откат (П1). |
| `touches`, `not_touched`, `expected_codes` | Границы и ожидаемые отказы (массивы строк). |
| `artifact_zip`, `artifact_sha256` | Путь к выпуску от корня, ожидаемый SHA-256. |
| `checks` | Приёмка (П5), см. таблицу ниже. |
| `findings` | `{id, text, basis, criterion, effect}` — выводы П6. Измеренные значения читаются из проб, а не дублируются вручную. |
| `not_run` | `{what, why}` — работы вне фактического прогона, даже если список пуст. |
| `seal_members` | Пути от корня. Обязательны спецификация, результаты проб, `ACCEPTANCE.json`, итоговый `REPORT.md`. Не включать `SEAL.json`, `REPLAY.json`, страницу или сам ZIP. |
| `next` | Следующий шаг, без его запуска. |

Пути внутри спецификации — канонические относительные пути с `/`, без `..` и символьных ссылок. У проверки обязательны непустые `name`, `basis` и `criterion`. Структурный пол: не менее восьми уникальных имён, хотя бы одно сравнение **свежей** пробы с существующим эталоном вне каталога выхода. Этот пол не заменяет сверку смысла критериев (П0 и П9).

## Проверки

| `type` | Дополнительные поля | Что доказывает |
|---|---|---|
| `json_equal` | `source`: `baseline` или `cleanroom`; `reference` | JSON свежей пробы совпадает с независимым эталоном целиком. |
| `json_value` | `source`: `baseline`, `cleanroom` или `release_tests`; `path`, `op`, `value` | Сравнивает поле (`==`, `!=`, `>`, `<`, `len==`); путь точечный, для массива — числовой индекс. |
| `steps` | `expect: [{step, поле: значение}]` | Каждый указанный шаг и поле присутствуют и совпадают. Отсутствие поля не равно `null`. |
| `surfaces_absent` | — | Все шесть запланированных поверхностей измерены и отсутствуют. |
| `deterministic` | `source`: `baseline` или `cleanroom` | Первичный сохранённый результат совпадает с независимым повтором. |

## Порядок и артефакты

1. **П3:** измерение архивного выпуска из репозитория (`BASELINE.json`).
2. **П4:** чистая копия `install → connect → create` без калибровки (`CLEANROOM.json`); в **другой** распаковке — офлайн `kit/tests` (`RELEASE-TESTS.json`, со своими пропусками).
3. **П5:** проверки, вердикт и `not_run` со статусом и причинами (`ACCEPTANCE.json`). Пропуски считаются отдельно от `pass`. Вердикт этого файла — только П5, не закрытие всей итерации.
4. **П6:** окончательный `REPORT.md` из спецификации и машинных результатов.
5. **П7:** ZIP конечных файлов, `SEAL.json` (размер и SHA-256) и `REPLAY.json` (сравнение с повторной сборкой). После печати харнесс не переписывает её входы. Это проверка целостности, не подпись.
6. **П8:** `Итерация-<id>.html` из приёмки, печати и результатов. CLI возвращает успех, только если прошли приёмка, повтор и создание страницы.

## Дополнительная проба без изменения базовых измерений

И‑103: `python3 -B research/103/run.py` (те же `--dry-run` и `--verify-seal`). Доверенный Python-драйвер передаёт `main(..., extra_probes={"имя": ("ИМЯ-ФАЙЛА.json", функция)})`. Функция получает путь к уже сверённому ZIP и возвращает данные для JSON; она не запускается при `--dry-run` или `--verify-seal`. Для такой пробы `json_value.source` принимает зарегистрированное имя, а `seal_members` обязан включить её результат. Спецификация не задаёт исполняемые команды. Необязательный `test_file` — запечатанный `test_*.py`, на который ссылается отчёт; фикстуры исполняются отдельно.

П0–П2 и П9 остаются отдельными шагами: подготовка замысла и фикстур, сверка стратегии, `commit/push`. Негативные сценарии базового харнесса: `python3 -B research/102/test_harness.py`.
