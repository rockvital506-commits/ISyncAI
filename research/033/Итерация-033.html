Как теперь выглядит слияние

Владелец тянет изменения и получает конфликт в .agent-contract/project/checks.json:

  1. git show :3:.agent-contract/project/checks.json > .agent-contract/project/checks.incoming.json — входящая версия сохранена файлом;
  2. git checkout --ours -- .agent-contract/project/checks.json — рабочая остаётся локальной;
  3. plan {"op": "merge", "incoming": ".agent-contract/project/checks.incoming.json"} — видно, что добавится и что уже известно;
  4. apply с билетом — объединение записывается обычной операцией, с журналом и резервной копией;
  5. git add -A && git commit — слияние завершено.

Находка F14. merge добавляет записи, но не сводит разногласия: если две машины записали одно событие с разными исходами (pass локально, fail в облаке), входящая запись отбрасывается как дубль. Для наблюдений это осознанно — расхождение показывает проверка, а не слияние. Но владелец должен знать, что merge промолчит; сведение расходящихся исходов — отдельный предмет.
Про «условно». Живые VS Code, Kilo и Copilot не запускались; модели не вызывались; платформа подаётся как объявленные данные. Всё это записано как not run. «Две машины» здесь — две копии проекта, соединённые git, с разными объявленными данными (F13).
