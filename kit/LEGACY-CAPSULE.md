# Снимок трёх старых документов: сохранение и чтение

Это промежуточный механизм для `0.1.36 → v2`, **не мигратор, не установка и не откат**.
Он работает только с переданными байтами, не ищет файлы проекта, не запускает старый Kit и
не пишет контейнер на диск. Никаких пользовательских данных для разработки не использовано.

## Python API

```python
from kit.legacy_capsule import prepare, inspect, extract, read_history

result = prepare({'state': state_bytes, 'checks': checks_bytes, 'base_rules': base_rules_bytes})
archive = result['archive']
pin = result['archive_sha256']
summary = inspect(archive, pin=pin)
original_bytes = extract(archive, pin=pin)
history = read_history(archive, pin=pin)  # Явно возвращает содержимое истории и проверок.
```

Все три входа обязательны и не больше 2 МиБ каждый. `prepare` хранит байты как данные,
даже если они не являются правильным JSON: это позволяет сохранить неисправный образец для
диагностики, но **не** делает источник здоровым. `extract` возвращает точные байты по
логическим именам, а не создаёт файлы. Эти байты можно явно передать в `compare_old.compare`.

Контейнер — канонический ASCII JSON с фиксированными тремя именами и стандартным base64,
размерами и SHA-256 каждой части. Одинаковые байты дают одинаковый контейнер и SHA-256.
При чтении всегда требуется pin всего контейнера, а затем проверяются состав, каноническая
форма, размеры и хеши членов. Ошибка даёт `CapsuleError` и не выдаёт частичный результат.
Pin, взятый из того же недоверенного контейнера, не доказывает его происхождение; даже
независимый pin сравнивает байты, а не заменяет подпись или установление полномочий.

## Чтение истории и проверки

`inspect` возвращает только размеры и хеши, без тел. `read_history` дополнительно читает JSON
state и checks, проверяет заявленные версию `0.1.36`/схему 1, типы списков и число решений
относительно ревизии. Возвращает `decisions`, `tombstones` и `checks` **как были в JSON**.
Это ограниченный просмотр: не выполняется полная валидация нативного старого Kit, даты,
подписи, содержимого решений или базы; старый журнал не превращается в журнал v2. Ответ
содержит `source_health: not_checked`, `legacy_history_imported: false` и
`migration_ready: false`. `base_rules` хранится побайтно, но `read_history` его не разбирает.

## CLI и конфиденциальность

`python3 -I -S -B kit/legacy_capsule.py` принимает один JSON через stdin и выдаёт один JSON
на stdout. Варианты: `format: 1`, `action: "prepare"` и `source` с тремя значениями base64;
или `format: 1`, `action: "inspect"` / `"history"`, `archive_base64` и `pin`. `prepare`
возвращает `archive_base64` и его SHA-256. `inspect` не выводит исходные тексты, а
**`history` намеренно возвращает содержимое решений и проверок**. Код `0` означает выполнение
команды, не успешную миграцию; ошибка — код `1` и диагностический код без входных значений.

Архив, запросы, история и даже хеши могут содержать чувствительные сведения. Не передавайте
их в чат или внешнюю модель; используйте только свои данные и доверенные процессы. Код не
управляет правами на stdin/stdout, буферы, журналы ОС или сохранённые вызывающим файлы.
Нельзя считать base64 шифрованием.

Снимок содержит **только три** явно заданных документа. В нём нет установленного манифеста
и остальных файлов базы, снимков операций, pending-транзакций, прав, настройки среды и
проектных файлов. Его наличие не подтверждает целостность установки, безопасность источника,
восстановимость после сбоя, поведение нового runtime или ворота И-131/132 и G5. Полный
согласованный снимок и собственно миграция по-прежнему необходимы.
