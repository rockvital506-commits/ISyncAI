# Хранилище v2: раздельные области

[Схема v2](SCHEMA-V2.md) проверяет документ, а [`registry_store.py`](registry_store.py) — узкий внутренний порт для **существующего** рабочего дерева. Python ≥ 3.10, стандартная библиотека, без старого Kit и ISAI. Это не установщик и не пользовательский CLI.

## Привязка

`Layout(workspace, profile_root)` вызывающий код задаёт явно: `workspace` — существующий абсолютный рабочий каталог, `profile_root` — выбранный относительный каталог профиля внутри него. Например:

| Область в одном рабочем дереве | Декларируемый `roots` | Файл v2 |
|---|---|---|
| L0 | `["kit"]` | `kit/base/registry.json` |
| L1 (пример) | `["profiles/pilot"]` | `profiles/pilot/registry.json` |
| L2 | `[".agent-contract"]` | `.agent-contract/project/registry.json` |

В этой раскладке один корень принадлежит выбранному профилю, не всему каталогу `profiles`. L1 выбирают **в контексте вызова**, не по полю в JSON или по `scope`. Три корня не могут совпадать или быть вложенными; пути к ним и реестрам проверяются на ФС. Внутри рабочего дерева не используются символические ссылки или объекты с reparse-меткой на проверяемых путях; файл реестра с несколькими жёсткими ссылками отклоняется. Каждый реестр загружается с `expected_area`, единственный `roots` должен совпасть с привязкой. Для L1 при наличии [контейнера с журналом](PROFILE-JOURNAL.md) проверяются его внутренний реестр v2 и история. Сломанный, отсутствующий или чужой документ не считается пустым; читатель ничего не создаёт и не исправляет.

## Внутренний вызов

- `status(layout)` читает `schema_version`, `release_version`, `profile_root`, `profile_revision` и `project_revision` из заново проверенных файлов. Ревизии не выводятся одна из другой и не берутся из Git.
- `read_registry(layout, target=...)` возвращает проверенный реестр выбранной области. Не активирует, не сливает записи и не заменяет будущую пользовательскую команду `list`. `report_conflicts(layout)` возвращает диагностические пары, не изменяя их.
- `plan_create(layout, entry, target='L1')` показывает ровно одно добавление `rule` в состоянии `draft`, целевой файл и переход ревизии. Проверяет локального родителя и остальные требования схемы к будущему реестру; не пишет.
- `apply_create(layout, plan, confirmed_ticket=...)` принимает отдельное подтверждение именно показанного плана. Перед записью заново загружает состояние и сравнивает план, привязанный к рабочему каталогу, файлу, байтам текущего L1 и диффу. Билет — техническая привязка, **не** проверка личности, не полномочие и не способ получить согласие. Вызывающая сторона не должна самостоятельно подтверждать пользовательскую работу. Промпт, дозапрос и полноценный пользовательский цикл — Ф2.
- При успехе файл L1 с записями, `revision + 1` и строкой журнала заменяется из временного файла рядом с ним; L0 и L2 не имеют пути записи в этом порте. Возвращается `status` перехода. Нет активации, разрешения конфликтов или автоматического повторного выполнения.
- `profile_history(layout)` — чтение локальных решений о принятых регистрациях. Для старого голого реестра v2 история не додумывается, а файл не переписывается. `no_change` и ограничения повторного подтверждения описаны в [контракте журнала](PROFILE-JOURNAL.md).

[Матрица допусков](OPERATION-MATRIX.md) отличает запрет L0 от ещё не реализованной операции. При создании проверяются `target`, привязка, реестры и предлагаемый дифф; совпадение билета не снимает запреты. Новую запись не сохраняют при обнаруженном структурном противоречии, в том числе появившемся после плана.

`StoreError.diagnostic()` даёт `code` и `where` (относительный путь или имя параметра), вложенные `schema.stage/code/path` при ошибке данных и `details.conflicts` при противоречии. Ошибки связи предлагаемой записи дают `parent`, прочие ошибки её формы — `invalid_entry`. A1–A4 и допуск описаны в матрице; отдельные причины хранилища сохраняются (`unsafe_path`, `missing_path`, `root_mismatch`, `invalid_registry`, `invalid_history`, `unsupported_entry`, `entry_exists`, `confirmation_required`, `stale_revision`, `plan_mismatch`, `write_failed`).

## Граница проверки

[И‑105](../../research/105/REPORT.md) испытывает этот порт на обычном локальном Linux-дереве с одним писателем. Сравниваются состав и байты всех файлов в корнях, отдельно SHA‑256 тестового манифеста и значения ревизий. Снимок не включает время доступа или права. Из замены одного файла не следуют стойкость к сбою питания, безопасность отдельно взятого каталога при параллельной замене путей, изоляция mount namespace, поддержка Windows/NTFS/junction/ACL, доверие к манифесту или авторизация владельца. Другие процессы не ограничены этим портом.
