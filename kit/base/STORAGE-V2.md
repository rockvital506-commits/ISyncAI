# Хранилище v2: раздельные области

[Схема v2](SCHEMA-V2.md) проверяет документ; [`registry_store.py`](registry_store.py) — внутренний порт для **существующего** рабочего дерева. Python ≥ 3.10, стандартная библиотека, без старого Kit и ISAI. Это не установщик и не пользовательский CLI.

## Привязка

`Layout(workspace, profile_root)` вызывающий код задаёт явно: `workspace` — существующий абсолютный рабочий каталог, `profile_root` — выбранный относительный каталог профиля внутри него. Например:

| Область | Декларируемый `roots` | Файл v2 |
|---|---|---|
| L0 | `["kit"]` | `kit/base/registry.json` |
| L1 (пример) | `["profiles/pilot"]` | `profiles/pilot/registry.json` |
| L2 | `[".domain-agent-kit"]` | `.domain-agent-kit/project/registry.json` |

L1 выбирают **в контексте вызова**, не по полю JSON, фразе, метке `authority` или `scope`. Три корня не могут совпадать или быть вложенными; пути к ним и реестрам проверяются на ФС. Внутри рабочего дерева на проверяемых путях не используются символические ссылки, объекты с reparse-меткой и файлы реестров с несколькими жёсткими ссылками. Каждый реестр проверяется с ожидаемой областью и с `roots` из `Layout`. L1/L2 могут иметь [контейнер с журналом](REGISTRY-JOURNAL.md); проверяются и вложенный v2, и история. Сломанный, отсутствующий или чужой документ не считается пустым; читатель ничего не создаёт и не исправляет.

## Вызовы и запись

- `status(layout)` читает `schema_version`, `release_version`, `profile_root`, `profile_revision`, `project_revision` из заново проверенных файлов. Ревизии не выводятся друг из друга или из Git.
- `read_registry(layout, target=...)` возвращает проверенный реестр области, `report_conflicts(layout)` — структурные пары; это не чтение эффективной политики. `registry_history(layout, target='L1'|'L2')` возвращает проверенный журнал; `profile_history` сохраняет совместимый вызов для L1. Чтение не добавляет историю старым данным.
- Пользовательский путь — [сессия карточки](OPERATION-PLAN.md), с допуском по [матрице](OPERATION-MATRIX.md). Она отделяет список от мутаций. Актуальность проверяется по `revision` цели, входным SHA‑256 трёх реестров и будущим байтам перед заменой; на POSIX также сравниваются наблюдённые mode-биты трёх файлов, на других ОС — `not_checked`. Перед записью temp на POSIX также сверяются mode/UID/GID цели и открытого temp; несовпадение блокирует замену. UID/GID на момент плана, ACL и гарантии после замены не проверяются; гонки остаются. Параллельные писатели могут затереть подтверждённое решение даже при двух ответах `applied`; отсутствие других писателей и подмены файлов/каталогов не проверяется. Для purge нужно ещё `allow_delete is True`. Остальные файлы и корни не являются целями.
- Исторический нативный API `plan_create(layout, entry, target='L1')` / `apply_create(layout, plan, confirmed_ticket=...)` обслуживает только `rule/draft` L1. Нативный билет связан с рабочим каталогом, байтами L1 и точным добавлением; одно его наличие не даёт согласия или прав. При дополнительном `preview=preview_create(...)` сверяются SHA‑256 всех трёх реестров и будущие байты. Это совместимость И‑105–109, не новый нативный маршрут для L2 или остальных действий.
- Оба пути используют одни проверки будущего реестра и один вызов замены. При успехе временный файл создаётся **рядом с целью** и `os.replace` заменяет файл с реестром, `revision + 1` и решением вместе. Никаких отдельных файлов истории, записи в L0 или смены соседней ревизии. При наблюдаемом отказе временный файл удаляется; отказ удаления диагностируется отдельно. Успех возвращает `status` перехода, а не удостоверение применения правил.

`StoreError.diagnostic()` возвращает `code`, `where` (относительный путь или реквизит), вложенную `schema.stage/code/path` при диагностике схемы и `details` для уточнения причин (`rule_conflict`, `parent`, `invalid_transition`). Коды и допуски описаны в матрице и сессии. Повреждённый журнал — `invalid_history`, а не команда пересоздания.

## Граница проверки

[И‑105](../../research/105/REPORT.md) и [И‑110](../../research/110/REPORT.md) проверяют обычное локальное Linux-дерево, один писатель. Сравниваются состав и байты корней, физические замены, метки обычных файлов и SHA‑256 тестового манифеста. Не обещаются неизменность времени доступа, авторизация, права ОС, ACL/NTFS, безопасность при параллельной замене путей или устойчивость к сбою питания. Другие процессы не ограничены портом. Удаление из текущего реестра не стирает Git или внешние копии.
