# L1/L2 · история манипуляций, `registry_format: 2`

[И‑110](../../research/110/DESIGN.md) сохраняет реестр v2, ревизию и решение **в одном файле выбранной области**. `registry_format` — тег внешнего контейнера, не версия схемы v2 или продукта. L0 не использует этот контейнер.

| Поле | Что содержит |
|---|---|
| `registry` | Текущий реестр [v2](SCHEMA-V2.md), включая `revision` и связи. |
| `journal.base_revision` | Ревизия, от которой известна последовательность решений. |
| `journal.base_entries` | Объект `ID → SHA‑256` для базового состояния. Не набор выдуманных решений. |
| `journal.decisions` | По одному решению с `operation`, `entry_id`, `profile_revision` для L1 либо `project_revision` для L2, `before_sha256`, `after_sha256`. Ревизия в решении — **после** записи. |

Отпечаток — SHA‑256 компактного JSON записи с отсортированными ключами и ASCII-экранированием без завершающего перевода строки, как в [формате 1](PROFILE-JOURNAL.md). У `create` нет прежней записи (`before_sha256: null`); у `delete` нет новой (`after_sha256: null`). У `edit`, `suspend`, `resume`, `revoke` два разных отпечатка. Читатель проверяет структуру, шаги ревизии без разрывов, совпадение каждого прежнего отпечатка с состоянием цепочки и равенство итоговой карты отпечаткам текущих записей. ID с наблюдаемым удалением не регистрируется заново (`entry_retired`). Неизвестный старый ID нельзя считать удалённым только по номеру ревизии.

## Чтение старой формы

- Голый v2 L1/L2 читается без записи: `registry_history(layout, target=...)` возвращает его `revision` как `base_revision` и пустой список `decisions`. При первой записи формата 2 базовая карта строится по фактически прочитанным записям.
- L1 `profile_format: 1` проверяется и возвращается в прежней форме; регистрация `rule/draft` в голый L1 или формат 1 сохраняет совместимый путь. При первой записи формата 2 прежнее `create` сохраняет ID, ревизию и отпечаток как `after_sha256`. Базовая карта содержит только те начальные записи, которые не входят в ряд этих `create`. Следующие изменения уже не возвращают формат 1.
- `profile_history(layout)` читает выбранный L1, как и `registry_history(..., target='L1')`; оба делегируют проверке реестра и истории. Неверный журнал даёт `invalid_history`, неверный внутренний реестр — `invalid_registry`. Чтение не переписывает форму. Нет автоматического отката к формату 1 для старых читателей и нет миграции 0.1.36.

Редактирование и смена состояния оставляют предыдущие решения в порядке ревизий. Отмена оставляет текущую запись и её текст; отдельный подтверждённый purge удаляет запись **из текущего файла**, оставляя ID и отпечатки в истории. Старая формулировка не восстанавливается из хеша. Журнал не доказывает прежние состояния или соблюдение правил, не содержит подписи, имени владельца, его согласия, путей машины или времени. Он хранит не тела прошлых версий, а проверяемую последовательность локальных изменений. Замена всей истории или удаление из Git/резервных копий за этой границей.
