# Операции и области: внутренний порт v2

[`registry_policy.py`](registry_policy.py) — исполняемая таблица; [`registry_store.py`](registry_store.py) экспортирует `operation_matrix()` и `check_operation(operation, target=...)`. Первое возвращает свежий снимок `операция → область → {state, code}`; второе — доступную ячейку или `StoreError`. Это **допуск пары**, а не обещание, что документы, билет, связь с профилем или права позволят её выполнить.

- Восемь пользовательских действий идут через [`PlanSession`](OPERATION-PLAN.md); **14 исполненных ячеек И-110** и наблюдавшиеся тогда переходы — [ACTIONS.json](../../research/110/ACTIONS.json). `list` не равен `read`: возвращает каталог или отдельный текст, а не сырой реестр. Нативный `plan_create/apply_create` сохранён только для `rule/draft` L1, не подменяет карточный маршрут L2.
- `available` имеет `code: null`, `planned` — `operation_unavailable`, `forbidden` — `system_immutable` для любой эксплуатационной мутации L0. Внешнее `authority` или билет не меняют цель. Имя вне таблицы — `unknown_operation`; неизвестная область — `unknown_area`.
- `status`, `profile_history`, `registry_history`, `report_conflicts` — диагностические чтения. Повреждённая привязка или данные любой области блокируют загрузку. Bootstrap, промоушен, перенос, выдача прав и команды донора не входят в матрицу. [Опытный двухсторонний план](MOVE-PREVIEW.md) только вычисляет гипотезу в памяти и не реализует перенос. [Снимок И‑107](../../research/107/MATRIX.json) исторический, не текущий допуск.

## Причины A1–A4

| Инвариант | Код операции | Конкретная причина |
|---|---|---|
| A1 | `profile_root_conflict` | Совпадение/вложенность корней или совпавшая идентичность выбранных каталогов. `where` — привязка L1. Ссылки, отсутствующий путь, чужой корень имеют отдельные коды. |
| A2 | `system_immutable` | Цель L0 определяется до трактовки данных или билета. Чужой `authority` при нативной цели L1 — `invalid_entry` / `authority_area`; форсированное поле карточки — `card_mismatch`. |
| A3 | `rule_conflict` | `where: entries`, `details.conflicts` показывает обе записи в каждой паре; нет победителя или автокоррекции. |
| A4 | `parent` | Схема даёт `parent_missing`, `parent_kind`, `scope_outside` и другие причины в `schema`. Возобновление под неактивным контрактом и попытка удалить контракт с детьми дают `details.reason`. Нарушение сохранённой схемы — `invalid_registry`. |

## Структурный отчёт A3

`report_conflicts(layout)` возвращает `{key, scope, entries: [{area, id, scope, value, text}, …]}` для каждой пары. Сравниваются активные неконтрактные записи **под активным локальным контрактом**, с явным `key/value`. Равный ключ, разные значения и пересечение `scope` дают пару, в том числе внутри одной области. `scope` пары — более узкая общая область. Порядок ключей, областей и ID нужен для воспроизводимости, не для старшинства. Свободный текст не интерпретируется.

При предлагаемой мутации проверяются текущее и будущее состояния; обе проверки повторяются при согласованной записи. Точный `no_change` не пишет независимо от отчёта о противоречиях. Обычное чтение не блокируется наличием пары, не решает конфликт и не является `promote`. Полный разбор ограничений, приоритетов и решения владельца — И‑116.
