# План создания производного правила для Kilo

Это узкий механизм создания **одного нового файла**, не установщик Kit и не настройка Kilo.
Он работает только с уже существующими тремя реестрами и каталогом `.kilo/rules`. Он не
создаёт папки или `kilo.jsonc`, не изменяет `AGENTS.md`, не переписывает существующие файлы
и не делает черновики действующими. `scope` уже чем `.` отвергается. Применение возможно
только после просмотра точного плана и отдельного подтверждения. Статус чтения Kilo: `not run`.

```text
python3 -B kit/kilo_deploy.py --workspace /absolute/workspace --profile-root profiles/pilot
```

Процесс принимает по одному UTF-8 JSON на строку и отвечает JSON на stdout:

```json
{"type":"plan","area":"L1","entry_id":"R-1"}
```

Формат плана — `plan_format: 2`; относительно предыдущего кандидата добавлен `staging_target`.
План показывает `target`, `staging_target` (временный файл), полный `content`, SHA-256
содержимого и трёх реестров, а также разовый `ticket`. После проверки владельцем передать
**в том же процессе** полный план и отдельно подтверждённый билет:

```json
{"type":"apply","plan":{"...":"полный ответ plan"},"confirmed_ticket":"подтверждённый билет"}
```

Это схема, а не готовый применимый JSON. `{"type":"cancel"}` отзывает ожидание. Успех —
`created` с относительным путём и SHA-256; файл появляется с именем `kit-l1-<ID>.md` или
`kit-l2-<ID>.md`. Повторный план, если файл уже существует, отказывает — обновление/удаление
существующего материала здесь не реализовано. Убедитесь, что Kilo настроен на чтение этого
каталога, но не изменяйте конфигурацию автоматически; реальный прогон проводится отдельно.

При изменении источника или каталога между планом и применением операция отказывает.
Запись сначала идёт в новый временный `.tmp` с путём `staging_target`, затем проверяются
`fsync` и точные байты. Только после этого создаётся жёсткая ссылка на новое имя `.md`;
существующее имя не заменяется. Затем временное имя удаляется. Если файловая система не
поддерживает такую ссылку, возвращается `publish_failed`, небезопасного запасного способа нет.
Это проверено в синтетическом Linux-стенде, но не на Windows, конкретной файловой системе
владельца или в работающем Kilo. Другой процесс всё ещё может читать временный файл.

При `staging_exists` чужой временный файл не перезаписывается. `write_failed` и
`publish_failed` сопровождаются попыткой удалить только созданный временный файл.
При `cleanup_failed`, `cleanup_unsafe` или `created_unverified`, а также при внезапном
завершении процесса, состояние считать неопределённым: остановиться и проверить оба пути
из плана, их идентичность и хеши до принятия решения о восстановлении. Могут остаться оба
имени одной жёсткой ссылки; ничего другого автоматически не удаляется. После повторного
запуска старый билет недействителен. Долговечность при сбое питания не проверена.

Нет блокировки соседних процессов или полноценной защиты от гонок путей; запускать только при
отсутствии конкурирующих читателей и писателей. Текст инструкции не защищает файлы. Билет
не удостоверяет, что владелец видел или одобрил план. Тексты, план и временный файл могут
содержать данные профиля; не передавайте их в среду без соответствующих прав.
